# Internationalization

Aura ships in **English**, **European Portuguese**, **Brazilian Portuguese**,
and **Spanish**. This document is the contract both clients implement, so
mobile and web stay consistent and the message catalogs can later be merged
into one shared package.

## Locales

| Locale id | URL segment | `lang` / `hreflang` | `og:locale` | Intl format | Notes |
|---|---|---|---|---|---|
| `en` | *(none)* | `en` | `en_US` | `en` | Default and source language. All keys originate here. |
| `pt` | `/pt` | `pt-PT` | `pt_PT` | `pt` | European Portuguese. |
| `pt-br` | `/pt-br` | `pt-BR` | `pt_BR` | `pt-BR` | Brazilian Portuguese. |
| `es` | `/es` | `es` | `es_419` | `es` | Neutral Latin-American Spanish. |

`pt` maps to `pt-PT` deliberately: the URL stays short for sharing and
marketing, while the language tag stays correct for search engines and the
`lang` attribute. Brazilian Portuguese is a separate locale (`pt-br`). Do not
collapse `pt-BR` onto European `pt`.

English has **no URL prefix**. `/` stays the English site, so every link
already shared keeps working and the marketing URLs stay clean.

Spanish copy is **neutral LATAM** (`tú`, not `vosotros`). Format numbers with
`es` (thousands as `12.421`), not a regional tag that would invert the
separator.

## What is never translated

| Term | Reason |
|---|---|
| **Aura** | Product name and the in-game currency. Translating it would break the one word the whole product is built around. |
| Level titles: NPC, Aura Enjoyer, Aura Farmer, Aura Merchant, Aura Lord, Aura God | Deliberately English internet-culture terms. Speakers in this audience use them untranslated; localizing them would make the product read as older than it is. |
| Usernames, captions, user content | User-authored. |

Everything else — UI copy, empty states, errors, notifications, marketing —
is translated.

Product verbs stay as product words across catalogs: **like**, **farm** /
**farmar** / **farmear**. Do not replace them with softer local synonyms.

## Message format

**ICU MessageFormat**, in JSON catalogs, on both platforms.

Not academic: Aura is full of counts, and the languages pluralize differently.

```json
{
  "feed.post.likes": "{count, plural, one {# like} other {# likes}}",
  "feed.post.auraGain": "+{amount, number} Aura",
  "leaderboard.rank": "#{rank}"
}
```

Numbers and dates go through `Intl` with the active locale, never manual
string building. A hardcoded separator is wrong in one of the languages:

```text
en     12,421 Aura
pt     12.421 Aura
pt-br  12.421 Aura
es     12.421 Aura
```

### Format numbers with `pt` / `pt-BR` / `es`, never `pt-PT`

This one is easy to get wrong in a way that only shows up as the two apps
disagreeing:

| Locale passed to `Intl` | 12421 renders as |
|---|---|
| `en` | `12,421` |
| `pt` | `12.421` |
| `pt-BR` | `12.421` |
| `es` | `12.421` |
| `pt-PT` | `12 421` (narrow no-break space) |

CLDR's `pt-PT` uses a space as the group separator. We deliberately format
European Portuguese with **`pt`**, which yields the dot, because the Aura
number is the hero element of the entire product and a space reads as two
separate numbers at a glance.

So the locale is split by purpose, on purpose:

- **`pt-PT` / `pt-BR` / `es`** for `lang`, `hreflang`, and anything describing the language
- **`pt` / `pt-BR` / `es`** for `Intl` number and date formatting

Both apps must do this identically. Web formatting with `pt-PT` while mobile
formats with `pt` would show a different Aura total for the same user on the
same account, which is exactly the kind of divergence this document exists to
prevent. Adding a language means adding its formatjs locale data on mobile.

## Key naming

Namespaced by feature, lowercase, dot-separated:

```text
common.actions.retry
common.actions.cancel
feed.empty.title
feed.post.likes
leaderboard.you
errors.already_liked
```

Rules:

1. Keys are **identical across mobile and web** wherever the string means the
   same thing. The catalogs live in two apps today only because workspaces are
   not set up yet (`FND-03`); identical keys make consolidating them mechanical
   rather than a rewrite.
2. Never build a key at runtime by concatenation, or it becomes impossible to
   find unused strings.
3. Never concatenate translated fragments to form a sentence. Word order
   differs between languages; use one key with placeholders.

## API error codes are the translation boundary

The API is **locale-agnostic for client-facing copy**. It returns a stable
machine code, and the client renders the message:

```json
{ "error": { "code": "already_liked", "message": "You already liked this post" } }
```

`message` is for developers and logs. Clients must translate `error.code`
through the `errors.*` namespace and never display `error.message` directly.
This is the reason stable error codes exist, and it means adding a language
requires no backend deploy for those strings.

Both apps therefore need an `errors.*` entry for every code in
`apps/api/src/common/errors/error-codes.ts`, plus a fallback for unknown codes,
since a newer API can return a code an older app has never heard of.

Server-generated copy that reaches the user directly — push notifications,
emails — is different: it is rendered server-side, so `users.locale` stores the
user's language for that purpose. Waitlist and contact forms send the active
client locale (`en` / `pt` / `pt-br` / `es`).

## Web routing

Route segments are translated, so the URL reads naturally in each language:

| English | European Portuguese | Brazilian Portuguese | Spanish |
|---|---|---|---|
| `/leaderboard` | `/pt/classificacao` | `/pt-br/classificacao` | `/es/clasificacion` |
| `/about` | `/pt/sobre` | `/pt-br/sobre` | `/es/acerca` |
| `/feed` | `/pt/explorar` | `/pt-br/explorar` | `/es/explorar` |
| `/login` | `/pt/entrar` | `/pt-br/entrar` | `/es/entrar` |
| `/settings` | `/pt/definicoes` | `/pt-br/configuracoes` | `/es/ajustes` |
| `/terms` | `/pt/termos` | `/pt-br/termos` | `/es/terminos` |
| `/faq` | `/pt/perguntas` | `/pt-br/perguntas` | `/es/preguntas` |
| `/contact` | `/pt/contacto` | `/pt-br/contato` | `/es/contacto` |

Requirements:

- Locale detection from `Accept-Language` on first visit, with an explicit
  switcher in Settings (not the header). A user's choice wins over the
  header and persists. `pt-BR` must resolve to `pt-br`, not `pt`.
- `hreflang` alternates on every page, including `x-default`.
- Every locale's URLs in `sitemap.ts`.
- Localized metadata: title, description, and Open Graph per locale.

### Public post URLs stay unprefixed

`/a/:username/post/:postId` is the viral loop and gets shared to Instagram,
WhatsApp, and TikTok. That URL is **canonical and permanent**, with no locale
prefix. A leftover `/a/@username/…` (the `@` is how we *display* handles, not
a path segment — Next.js reserves `@slot` for parallel routes) 308s onto this
form. The page renders in the viewer's locale, and any localized variant
points its canonical link back to the unprefixed URL. The app deep link keeps
the `@`: `aura://a/@username/post/:postId`.

Locale prefixes on share URLs would fragment the link graph across languages
and turn a future routing change into dead links in other people's posts.

Waitlist referral shorts (`/r/:code`) follow the same unprefixed rule and
redirect to `/?ref=:code`.

## Mobile

- Detect the device locale on first launch (`expo-localization`), fall back to
  `en` for anything unsupported.
- `pt-BR` → `pt-br`. Other `pt-*` (`pt-PT`, `pt-MZ`) → European `pt`.
  `es-*` → `es`.
- i18next must use `load: 'currentOnly'`. `languageOnly` would collapse
  `pt-br` onto the European catalog.
- Offer an in-app override on the Settings screen, not the profile; the
  choice persists and wins over the device.
- Never assume string length. Portuguese and Spanish run roughly 15-25%
  longer than English, which is exactly enough to break a tab bar label or a
  button.

## Adding a language

1. Copy the `en` catalog, translate the values, keep the keys.
2. Register the locale in **both** apps and in the web routing config.
3. Add the route segment translations and landing section ids.
4. Add formatjs locale data on mobile. If the new id contains a region
   (`pt-br`), do not turn `load: 'languageOnly'` back on.
5. Add server-rendered email copy if the API owns any.
6. Verify the longest strings still fit.

Missing keys fall back to English rather than rendering a raw key.
