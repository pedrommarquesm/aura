# Internationalization

Aura ships in **English** and **European Portuguese**. This document is the
contract both clients implement, so mobile and web stay consistent and the
message catalogs can later be merged into one shared package.

## Locales

| Locale id | URL segment | `lang` / `hreflang` | Notes |
|---|---|---|---|
| `en` | *(none)* | `en` | Default and source language. All keys originate here. |
| `pt` | `/pt` | `pt-PT` | European Portuguese. |

`pt` maps to `pt-PT` deliberately: the URL stays short for sharing and
marketing, while the language tag stays correct for search engines and the
`lang` attribute. If Brazilian Portuguese is added later it becomes `pt-br`
alongside it, and `pt` keeps meaning Portugal.

English has **no URL prefix**. `/` stays the English site, so every link
already shared keeps working and the marketing URLs stay clean.

## What is never translated

| Term | Reason |
|---|---|
| **Aura** | Product name and the in-game currency. Translating it would break the one word the whole product is built around. |
| Level titles: NPC, Aura Enjoyer, Aura Farmer, Aura Merchant, Aura Lord, Aura God | Deliberately English internet-culture terms. Portuguese speakers in this audience use them untranslated; localizing them would make the product read as older than it is. |
| Usernames, captions, user content | User-authored. |

Everything else — UI copy, empty states, errors, notifications, marketing —
is translated.

## Message format

**ICU MessageFormat**, in JSON catalogs, on both platforms.

Not academic: Aura is full of counts, and English and Portuguese pluralize
differently.

```json
{
  "feed.post.likes": "{count, plural, one {# like} other {# likes}}",
  "leaderboard.rank": "#{rank}"
}
```

Numbers and dates go through `Intl` with the active locale, never manual
string building. Portuguese groups thousands with `.` where English uses `,`,
so a hardcoded separator is wrong in one of the two languages:

```text
en  12,421 Aura
pt  12.421 Aura
```

## Key naming

Namespaced by feature, lowercase, dot-separated:

```text
common.actions.retry
common.actions.cancel
feed.empty.title
feed.post.likes
leaderboard.you
errors.already_liked
```

Rules:

1. Keys are **identical across mobile and web** wherever the string means the
   same thing. The catalogs live in two apps today only because workspaces are
   not set up yet (`FND-03`); identical keys make consolidating them mechanical
   rather than a rewrite.
2. Never build a key at runtime by concatenation, or it becomes impossible to
   find unused strings.
3. Never concatenate translated fragments to form a sentence. Word order
   differs between languages; use one key with placeholders.

## API error codes are the translation boundary

The API is **locale-agnostic for client-facing copy**. It returns a stable
machine code, and the client renders the message:

```json
{ "error": { "code": "already_liked", "message": "You already liked this post" } }
```

`message` is for developers and logs. Clients must translate `error.code`
through the `errors.*` namespace and never display `error.message` directly.
This is the reason stable error codes exist, and it means adding a language
requires no backend deploy.

Both apps therefore need an `errors.*` entry for every code in
`apps/api/src/common/errors/error-codes.ts`, plus a fallback for unknown codes,
since a newer API can return a code an older app has never heard of.

Server-generated copy that reaches the user directly — push notifications,
emails — is different: it is rendered server-side, so `users.locale` stores the
user's language for that purpose.

## Web routing

Route segments are translated, so the URL reads naturally in each language:

| English | Portuguese |
|---|---|
| `/leaderboard` | `/pt/classificacao` |
| `/about` | `/pt/sobre` |

Requirements:

- Locale detection from `Accept-Language` on first visit, with an explicit
  switcher. A user's choice wins over the header and persists.
- `hreflang` alternates on every page, including `x-default`.
- Every locale's URLs in `sitemap.ts`.
- Localized metadata: title, description, and Open Graph per locale.

### Public post URLs stay unprefixed

`/a/@username/post/:postId` is the viral loop and gets shared to Instagram,
WhatsApp, and TikTok. That URL is **canonical and permanent**, with no locale
prefix. The page renders in the viewer's locale, and any localized variant
points its canonical link back to the unprefixed URL.

Locale prefixes on share URLs would fragment the link graph across languages
and turn a future routing change into dead links in other people's posts.

## Mobile

- Detect the device locale on first launch (`expo-localization`), fall back to
  `en` for anything unsupported.
- Offer an in-app override; the choice persists and wins over the device.
- Never assume string length. Portuguese runs roughly 15-25% longer than
  English, which is exactly enough to break a tab bar label or a button.

## Adding a language

1. Copy the `en` catalog, translate the values, keep the keys.
2. Register the locale in both apps and in the web routing config.
3. Add the route segment translations.
4. Verify the longest strings still fit.

Missing keys fall back to English rather than rendering a raw key.
